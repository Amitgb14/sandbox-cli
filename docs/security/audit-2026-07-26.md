# Security audit — 2026-07-26

Scope: `sandbox-cli` at `0.0.1beta.6`, branch `security/host-boundary-hardening`
(5 commits, 49 files, +4237/−289, of which 1749 lines are tests).

This is the record of a four-way audit, the twenty-two issues it found, and what
was done about each. Every finding below was **reproduced by execution** before
it was fixed, and every fix carries a test named after the exploit it prevents.

---

## Why the audit happened, and what it changed

The work started as a review of an external suggestion: build a credential
proxy, and stress-test it with an allowlisted host that `302`s to a blocked one.
Testing that turned up unrelated problems, which turned into a full audit.

The audit's central result reordered the whole plan. **The container→host
boundary did not hold.** A prompt-injected agent — the exact threat this tool
exists to contain — could reach host code execution, mount the host filesystem
read-write, and silently disable the egress allowlist while sandbox-cli reported
it was enforcing one.

That matters for sequencing. A credential proxy defends against an attacker who
has to *read* a key; the attacker we actually had could already run code on the
host, and the proxy would have added real credentials plus a TLS-interception CA
private key to a machine the container could already reach. **The boundary was a
prerequisite for the proxy, not a parallel workstream.** The proxy is still the
right next step, and is now a reasonable one.

## Threat model

Three attackers, in descending order of how much they matter:

1. **A prompt-injected agent** with read-write access to `/workspace` (including
   `.git/` and `.sandbox.yaml`) and to its own persisted HOME, which is
   bind-mounted as the container's `HOME`. This is the design case: sandbox-cli
   exists so this attacker is contained.
2. **A hostile repository** the user clones and runs sandbox-cli inside. No agent
   involvement needed — `git clone && cd && sandbox-cli claude` was the whole
   exploit for several findings.
3. **A co-resident container** on the docker bridge.

The invariant being defended: *nothing inside the container, and nothing written
into the workspace, can cause code to run on the host or reach a host path that
was not explicitly mounted.*

## Findings

All 22 confirmed by execution. Severity is the impact **before** the fix.

### A — A project `.sandbox.yaml` was fully trusted

The file travels with the repository and the agent can rewrite it between runs,
yet every key in it outranked the user's own `~/.config/sandbox/config.yaml`.

| # | Finding | Severity |
|---|---|---|
| A1 | `secrets.<N>.command` ran arbitrary commands **on the host** via `sh -c`, before any container started. Also a pure supply-chain vector: no agent required. | Critical |
| A2 | `mounts: [{host: /, mode: rw}]` + `user: root` + `seccomp: unconfined` + `cap_add: [SYS_ADMIN]` all applied with no validation | Critical |
| A3 | `image: "--privileged"` was argument injection into the docker argv; the guest's first argument became the image name | Critical |
| A4 | `workdir: /usr/local/bin` mounted the repo **over** the directory holding `sandbox-firewall`, so root executed the repository's own file and no firewall was programmed | Critical |
| A5 | `network: {mode: default}` silently switched off an allowlist configured in the user's own config | High |

### B — Host-side git ran inside a repository the agent controls

git is a programmable tool: several ordinary features name a command in
`.git/config` or `.gitattributes` and then run it. The snapshotter runs
`git add -A` and `git update-ref` **every two minutes for the life of a run**, so
this was a *live* escape, not a next-invocation one.

| # | Finding | Severity |
|---|---|---|
| B1 | `filter.<x>.clean` executed on the host **while the sandbox was running** | Critical |
| B2 | `.git/hooks/reference-transaction` executed on the host during a default run | Critical |

`core.fsmonitor` was a third trigger on the same command; `recover show -p` and
`restore --patch` executed `diff.<x>.textconv` and `filter.<x>.smudge` — the
commands a user runs *after* a run they already distrust.

This also falsified a load-bearing comment in `snapshot.go` claiming "no hook
runs: these are all plumbing commands". Plumbing is not the same as inert.

### C — The mount guard covered only the workspace, and compared strings

| # | Finding | Severity |
|---|---|---|
| C1 | A forged `.git` **pointer file** (`gitdir: $HOME`) produced `--mount source=/,target=/` read-write. One file the agent already had write access to, firing on the user's *next* run — no hostile repo, no config | Critical |
| C2 | The home refusal compared strings after `EvalSymlinks`, which preserves the caller's casing while APFS/NTFS are case-insensitive. `--project /Users/AmitGhadge` mounted the home directory; `--project /USERS` bypassed the ancestor check and mounted every user's home | High |

### D — The agent's writable HOME was first on the root entrypoint's PATH

| # | Finding | Severity |
|---|---|---|
| D1 | The image set `PATH=/sandbox/home/.local/bin:${PATH}`, and in allowlist mode the entrypoint runs as **root** with `#!/usr/bin/env bash`. An agent wrote a file named `bash` into its own HOME; the next run executed it as root, and the firewall was never programmed | Critical |

Every precondition was a shipped default: persisted HOME is on unless
`--no-persist-auth`, agents install into exactly that directory, and this
repository's own `.sandbox.yaml` sets `network.mode: allowlist`.

### E — Env pass-through rendered after explicit env

| # | Finding | Severity |
|---|---|---|
| E1 | docker keeps the **last** `-e` for a repeated name, so forwarding `SANDBOX_RUN_AS` with `root` in the host environment made the entrypoint skip its privilege drop entirely | High |

### F — Network

| # | Finding | Severity |
|---|---|---|
| F1 | `INPUT`/`FORWARD` were unfiltered. `OUTPUT` accepts `ESTABLISHED,RELATED`, so a connection dialled *in* got a working reply path: a co-resident container pulled 30 bytes out of an allowlisted sandbox that could not reach `1.1.1.1` itself | High |

### G — Remaining findings

| # | Finding | Severity |
|---|---|---|
| G1 | Resolved secrets were `os.Setenv`'d into sandbox-cli's own process, which spawns `docker` and `git` afterwards — a secret named `PATH` or `DOCKER_HOST` redirected them, and the preflight ran *before* the injection | High |
| G2 | `recover repair` wrote outside the repository via an unvalidated `gitdir:` pointer, breaking rescue's stated "only creates refs under `refs/sandbox/`" rule | Medium |
| G3 | `--no-hardening` + `--allow` produced a container **wider** than either alone: docker's full default capset *plus* `NET_ADMIN`, with `no_new_privs` off | Medium |
| G4 | Config discovery walked to `/`, making a world-writable `/tmp` a config-injection point on Linux | High |
| G5 | Snapshots had no size cap; 60 MB of agent junk stayed pinned for 14 days, surviving its own deletion | Medium |
| G6 | `context list` titles and the `usage` model name reached the terminal unescaped — screen clears, window titles, OSC 52 clipboard writes | Medium |
| G7 | A symlink named `<uuid>.jsonl` in the persisted HOME made `context list` render an arbitrary host file | Low |
| G8 | `recover repair --branch NAME` was dead code; the advice the tool printed could never succeed | Low |
| G9 | Wrapper allowlists forwarded whole-account credentials (AWS, GitHub) silently | Medium |
| G10 | A missing `image:` was **built** from the embedded Dockerfile and tagged with that name, poisoning e.g. `node:22` in the local image store | Medium |
| G11 | `--workdir` moved `-w` but not the mount, starting the guest in a nonexistent directory | Low |
| G12 | `--user uid:gid` died under `--allow` with an opaque `id:` error | Low |

| G14 | `TestBuildArgs_OnlyDeclaredMounts` had an empty `if` body — the test pinning "no host-home path leaks into a mount" could never fail | Low |

## Remediation

Five phases, in severity order, each verified against the original exploit.

**Phase 0 — immediate.** Agent HOME off the image `PATH`; entrypoints use an
absolute interpreter and reset `PATH` before doing anything; `SANDBOX_RUN_AS` and
`SANDBOX_EGRESS_ALLOW` reserved and un-forwardable, with by-name forwards
rendered *before* explicit values; `image` validated plus a `--` guard;
`ValidateMountTarget` refuses any mount that shadows the container's own
binaries. *(D1, E1, A3, A4)*

**Phase 1 — the project-config trust boundary.** `internal/config/trust.go`
refuses the privilege-relevant keys from a discovered `.sandbox.yaml`. Network
settings use a direction-of-travel rule: a project may **tighten**
(`default → allowlist → none`), never loosen. Discovery is bounded to the
repository root, else `$HOME`, else the starting directory. *(A1, A2, A5, G4)*

**Phase 2 — host-side git.** `internal/githard` neutralises the config that makes
git run commands, for every git call sandbox-cli makes on its own behalf.
`GIT_CONFIG_GLOBAL`/`SYSTEM` were **not** the answer — the dangerous settings are
in the repository's *local* config, which those do not cover. Verified by
experiment:

| lever | neutralises |
|---|---|
| `-c core.hooksPath=/dev/null` | every hook, including `reference-transaction` |
| `-c core.fsmonitor=` | the fsmonitor command |
| `--no-textconv --no-ext-diff` | `diff.<x>.textconv`, `diff.<x>.command` |
| `GIT_ATTR_SOURCE=<empty tree>` | all clean/smudge filters |

The last is the interesting one: filter driver names come from `.gitattributes`
and are arbitrary, so there is no key to override — pointing the attribute stack
at an empty tree means no path ever selects a driver. *(B1, B2)*

**Phase 3 — mounts.** `GitCommonDir` requires the target to look like a real git
directory; `RefuseUnsafeHostPath` is exported and applied to the worktree `.git`
mount; path comparison is by device+inode rather than string. *(C1, C2)*

**Phase 4 — ingress.** `INPUT` is default-deny with three exceptions: loopback,
`ESTABLISHED,RELATED`, and the container ports named by `--publish`. *(F1)*

**Backlog.** All of G1–G14, plus `sandbox-cli ps`/`clean`, a run log at
`~/.config/sandbox/audit/sessions.jsonl`, and rate-limited iptables `LOG` rules
on both deny paths.

### Verification method

Two rules were applied throughout, and both caught real mistakes:

- **Nothing is fixed until the original exploit is re-run against the fix.**
- **Every fix is mutation-tested** — revert the fix, confirm its test fails with
  the original exploit visible in the output. A test that cannot catch the
  deletion of the thing it tests is close to worthless.

Three fixes were wrong on the first attempt and were caught this way: the symlink
check read the link's *target* rather than the link; `sandbox-cli ps` listed
nothing because `TrimSpace` ate trailing empty label fields; and a sanitizer
broke title truncation. A fourth was over-broad — banning the whole `SANDBOX_*`
namespace silently broke a documented user opt-out, caught by the integration
suite.

One plan was wrong: Phase 2 originally specified `GIT_CONFIG_GLOBAL=/dev/null`,
which would not have worked. Found by experiment before implementation.

## Accepted limits

Deliberate, and recorded so they read as decisions rather than oversights.

- **The firewall runs in allowlist mode only.** Filtering ingress on every run
  would mean every run taking the root-entrypoint path with `NET_ADMIN` — a worse
  default than the one it would protect.
- **`worktree.Git` is not hardened.** `sandbox-cli worktree git …` is the user
  running their own git in their own repository, where hooks firing is expected.
- **`GIT_ATTR_SOURCE` needs git 2.40+.** On older git it is ignored silently and
  clean filters are not neutralised; the other overrides still apply. Tracked.
- **git-lfs repositories** now snapshot real file content rather than the
  pointer — larger, but the more useful thing for a rescue copy.
- **`--config <path>` is trusted.** Typing the path is the deliberate act that
  discovery never involves; it is the escape hatch for a checked-in config you
  have read.

## Breaking change

A project `.sandbox.yaml` holding any refused key now errors, naming the key.
Move them to `~/.config/sandbox/config.yaml`, pass them as flags, or load the file
explicitly with `--config`. `sandbox-cli init` no longer scaffolds keys it would
then refuse.

## Still open

Tracked as tasks; none is a regression from this work.

| Item | Why it is still open |
|---|---|
| Egress matches resolved **IPs**, not names | `gist.github.com` is reachable under the baseline via `github.com`'s address, and it was never listed. Needs name-based enforcement — a CONNECT proxy, which does **not** require TLS interception |
| Names resolve once at container start | A rotating record breaks a domain the user did allowlist, mid-session. Same fix |
| The agent still holds raw credentials | The original request. Needs TLS interception, which makes the proxy the highest-value target in the system — an explicit decision, not a sub-bullet |
| DNS is open to any destination | Needed so the allowlist can resolve; also an exfiltration channel outside it |
| IPv6 rules are best-effort (`\|\| true`) | Fails open on a host without `ip6tables`, unlike the rest of the firewall |
| Denial logging is hard to read under Docker Desktop | Lands in the VM's kernel buffer; the run log is the portable half |
| Cross-project persistence | The persisted agent HOME and `--cache` volumes are shared across projects by design; neither is documented as a risk |

## Re-audit — same day, after the fixes

A second four-way audit was run against the fixed code: one auditor tasked only
with **breaking the fixes**, one auditing the ~4,200 lines the remediation added,
and two fresh passes over the container/network and host-side surfaces. It found
that one fix was incomplete and surfaced eight issues the first audit missed.

### The incomplete fix — R1, critical

**`GIT_ATTR_SOURCE` was never enough on its own.** Phase 2 reasoned about
`.gitattributes` in the working tree and treated the attribute stack as a single
source. It is not: git *always* additionally reads `$GIT_DIR/info/attributes`, a
gitdir-local file with **no `-c` override**. An agent writing
`.git/info/attributes` plus a `filter.<x>.clean` in `.git/config` had its command
executed on the host again by the next snapshot — reproduced end to end through
the real binary, and again on `recover restore --into-worktree` via the smudge
filter.

The corrected fix stops chasing attribute layers, because that side is unbounded
— arbitrary driver names, several layers, one with no override. A filter runs
only if an attribute selects a driver **and** that driver is *defined in config*,
and the definition side is bounded:

- `githard.Args(dir)` enumerates the repository's own `filter.*`/`diff.*` drivers
  and blanks each with `-c`. Layer-independent, and version-independent — unlike
  `GIT_ATTR_SOURCE`, which needs git 2.40.
- Snapshot content reads additionally run against a **scratch `GIT_DIR`** with
  `GIT_OBJECT_DIRECTORY` pointed at the real object store, so the repository's
  config is never consulted at all. Objects still land where recovery expects.
- `GIT_ATTR_SOURCE` stays as defence in depth for the window between enumeration
  and use.

### Also found and fixed

| # | Finding | Severity |
|---|---|---|
| R2 | **`BASH_ENV` gave root code execution before the firewall existed.** bash sources it at interpreter startup, so `--env BASH_ENV=/workspace/evil.sh` ran a workspace file as root with `NET_ADMIN` while `iptables` still read `-P OUTPUT ACCEPT` — and the guest afterwards still reported uid 1001. Pinning `PATH` in the scripts cannot help; the only place to stop it is before docker is invoked. `BASH_ENV`, `ENV`, `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, `SHELLOPTS`, `BASHOPTS`, `PS4`, `IFS`, `GLOBIGNORE` are now reserved | Critical |
| R3 | **`--user root` + `--allow` let the guest flush the firewall.** The entrypoint skips the privilege drop when the requested user resolves to uid 0, so the agent kept `NET_ADMIN` and ran `iptables -F OUTPUT`. The same contradiction as `--no-hardening` + `--allow`, which *was* refused; this case was missed. Now refused, for `root`, `0` and `0:0` | High |

### Found in the remediation's own code — fixed

The fourth auditor reviewed only the ~4,200 lines the remediation added, on the
principle that new code written fast is new attack surface. It was right to.

| # | Finding | Severity |
|---|---|---|
| R4 | **`network.allow` was permitted from a project file, and it *replaces*.** The permission was justified as "narrowing"; it is not — `allow` only widens, and `mergeInto` replaces rather than appends, so a checked-in file could rewrite an allowlist the user had configured. With `baseline: false` in the user's config, `allow: [exfil.example.com]` in the repository became the entire allowlist: the repository deciding where a compromised agent may send data | High |
| R5 | **A file named `*` silently killed the crash safety net.** `:(exclude)<path>` is a *glob*, so one oversized file with that name excluded everything and the snapshot captured nothing at all — for the rest of the run, with no message but "skipping \*" | High (data loss) |
| R6 | **The size cap did not apply to any filename git quotes.** `ls-files` without `-z` C-quotes non-ASCII paths, so `Lstat` failed and `rapport-financiér.bin` was pinned in the object store anyway. A newline in a name also split one path into two bogus lines | Medium |
| R7 | **The exclusion list was an unbounded argv and an unbounded map.** Enough oversized files produced "argument list too long", and three consecutive failures disable snapshotting for the run | Medium |
| R8 | **`sandbox-cli clean` destroyed unrelated containers.** Label values are branch names and repo paths; one containing a newline forged an entire row, whose Status parsed as empty — not `"Up"` — so `clean` force-removed a container sandbox-cli never created | Medium |
| R9 | `ports` and `snapshot` were permitted from a project file. `ports: ["0.0.0.0:8022:22"]` binds a host port on every interface *and* opens the default-deny INPUT chain; `snapshot: {enabled: false}` silently removes crash protection, and `interval: 1ms` is a sustained `git add -A` loop on the host | Medium |
| R10 | `--user <uid>` with no passwd entry died under `--allow` (`setpriv --init-groups` needs one). On Linux `--user $(id -u)` is how you get bind-mount ownership right, so correct ownership and the allowlist were mutually exclusive | Medium |
| R11 | A detached run wrote two audit records — a leftover pre-run stub beside the real one | Low |

R5–R8 and R11 were bugs in code written *during* the remediation, which is the
argument for auditing a fix as its own change rather than trusting that a fix is
safe because it is a fix.

The permitted set for a project `.sandbox.yaml` is now just `hostname`,
`cache.enabled`, and a `network.mode`/`baseline` that tightens. Three keys that
looked like project description turned out to be boundary decisions.

### Still open from the re-audit

Tracked as tasks: the port-53 tunnel; agent-written `.git/hooks` that the *user's*
own git executes; no isolation between sandboxes on the docker bridge;
published-port ingress accepting from any bridge source;
`host.docker.internal` reachable without `--host-gateway`; no seccomp profile
applied; unbounded memory/CPU; terminal injection via `git status -z` filenames
and the `context list` PROJECT column; an unbounded read of `~/.claude.json`; and
the structural point that `restrictedProjectKeys` is a hand-maintained denylist
over a growing struct with no completeness test — a new privileged field defaults
to *permitted*, silently.

### What the re-audit confirmed as holding

The privilege drop (`CapEff`/`CapPrm`/`CapAmb` all zero, `NoNewPrivs=1`, no file
capabilities anywhere, setuid binaries neutered); no writable directory on the
image `PATH`; fail-closed firewall setup; `INPUT` default-deny for unpublished
ports; IPv6 programmed default-deny; raw sockets and ICMP refused; the trust
boundary against YAML anchors, aliases and merge keys; the bounded config search;
inode-based path comparison; `validWorktreeAdminDir` against both direct and
symlinked targets; `BuildArgs` ordering and the `--` guard; and `ports.go`
parsing against argv injection.

### A note on method

Two of my own verification attempts nearly produced false positives: a backtick
in a shell probe ran `git worktree add` itself, and a `git checkout` in a test
setup fired the very filter I was testing for. Both were caught by re-running the
check with the marker cleared immediately before the command under test. When the
tool under test and the test harness use the same mechanism, attribution is the
hard part — clear state immediately before the action, never merely before the
script.
